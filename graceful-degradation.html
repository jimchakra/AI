Bend, don’t break

A general truth about complex chips serving shared, contended resources: you cannot meet a hard deadline by provisioning for the absolute worst case, because that worst case lives in contention on shared compute, not in the datapath. So design the datapath to bend — a built-in throttle that, when it predicts a miss, emits a bounded-loss result on time instead of stalling. The same silicon then stays reliable well past P99 with no added area, and the headroom you reclaim becomes a tiered-QoS product. Four live simulations below, worked through AI inference.

01The principle — complex chips can't provision the tail

This is a generic problem in any complex chip that serves shared, contended resources, and the subtlety is always the same: the datapath is rarely the risk. You size it, by construction, for the worst tolerated input within a fixed timeline — that part is deterministic. What is unbounded is what happens when many tasks share the same compute. A burst of cache misses, an interrupt storm, bus contention, memory-bandwidth pressure, or several tasks colliding on one core can stretch a task’s execution time with no warning — and no amount of headroom provisions the P100 of that tail. The uncertainty is never in the arithmetic; it originates in the shared compute resource — cache, bus, IRQ, scheduling, co-tenancy.

The disciplines that live under hard deadlines already know the answer: don’t block waiting for the worst case — detect that you will miss it and emit a bounded-loss result on time that the larger system is built to absorb, trading a small deterministic loss for the elimination of an unbounded, cascading one. Baseband modems do it (send a NACK, take one retransmission, rather than stall into a dropped call); storage controllers, network processors, and real-time control loops do their own versions. The point here is not that inference is a modem — it isn’t — but that inference serving has the same structure (a hard deadline, a datapath you can size, and a tail set by shared-resource contention you can’t), so the same design move applies. The rest of this page works that move through AI inference at two time scales, then shows the throughput and product payoff it unlocks.

02Layer 1 — token-deadline anytime KV degradation

A streaming decoder (voice, live translation, an agent in a control loop) owes one token every D ms. The deterministic part of a token’s cost — compute plus the KV read at the current context — is provisionable — you can size for it. What actually causes misses is the contention tail: co-tenant memory-bandwidth pressure, a kernel-launch or scheduler stall, a straggler rank in a tensor-parallel group. At short context there is slack to absorb those spikes; as context grows the deterministic baseline eats the slack, so the same contention spike begins tipping tokens over D. A rigid decoder rides it out and accumulates lag until the stream freezes. A decoder that can bend predicts the overrun and trims the KV budget to reclaim slack — emitting a slightly worse token on time. That is the throttle, and its quality cost is the measured Quest curve (budget → Δppl), not a guess.

Read it like a control-task time budget, not a link budget. Below the wall the two policies are identical — there is enough slack to absorb contention, so the throttle never engages and quality cost is zero. As context erodes the slack (or contention climbs), the rigid decoder’s on-time rate collapses and lag runs to tens of seconds (a frozen stream). The decoder that can bend converts that cliff into a gentle slope: it reclaims slack by reading less KV, paying a bounded per-token Δppl and staying on time. The deepest fallback, if even the smallest budget won’t fit (extreme contention), is to emit a hold/duplicate token — a true erasure, when even the throttle can’t make timing.

03Layer 2 — serving-side admission control vs congestion collapse

Now the deadline is a TTFT SLO and the tail is bursty arrivals. A single server (100 req/s capacity) faces load that spikes above capacity. A rigid server queues everything: under overload, latency explodes, every request misses the SLO, and timed-out clients retry — a storm that drives ~100% utilization doing ~0 useful work (congestion collapse). A robust server runs admission control: if the predicted wait exceeds the SLO, it rejects immediately with 503 + backoff — a throttle at the request level — so admitted work meets the SLO and goodput stays high. The rejected request is cheap and recoverable; the hung queue is not.

The retry storm is the point. Turn retry fraction up and watch the rigid curve fall toward zero rather than levelling off: a server that neither finishes work in time nor refuses it converts every client timeout into more load. Shedding breaks that loop — the same reason a modem NACKs early instead of letting a receive buffer back-pressure the whole pipeline. Tightening the SLO lowers the achievable plateau (less slack to absorb variance), which is the honest cost: admission control doesn’t create capacity, it protects the capacity you have.

04The throughput payoff — capacity vs the tail guarantee

First, the honest ordering, because it is easy to misread this as advocating a shaky system with a panic button. It is the opposite. The way you make a tight deadline safe is mixed-criticality partitioning: tight-deadline tasks get guaranteed resources — many tiny cores with SRAM scratchpad, no cache, no contention, so their worst-case execution time is deterministic by construction — while large throughput jobs run on powerful shared cores where timing uncertainty is accepted. Graceful degradation is the backstop for the residual tail that partitioning cannot kill (tail events still happen). And that backstop pays for itself in throughput.

The argument in one move: fix a latency-percentile guarantee and ask how much load a single server can carry while meeting it. Tighten the percentile and sustainable load collapses — you are spending capacity as insurance against a heavy contention tail. Keep the same percentile but truncate the tail with an anytime degrade (read KV until the deadline, then stop), and the tail cost migrates from missed deadlines to bounded quality loss — so you can run far hotter for the same guarantee.

The infeasibility point is the real headline. A gentle decline from P99 to P99.5 is just an insurance tax. But past roughly P99.8 the hard policy does not merely get expensive — it becomes impossible at any load, because a single contention spike makes one request’s service alone exceed the deadline, and no amount of idle headroom fixes a tail that crosses D. Truncation is the only thing that can. So an ultra-tight SLO tier is only offerable if you have an anytime-degrade capability — degradation is not a corner-cutting move, it is what makes the premium product feasible.

Tiered QoS — the business model this unlocks

The reclaimed capacity is sellable as differentiated QoS. Not every request wants the same guarantee: a radiologist reading a scan wants the highest tier — full quality, tightest latency, no degradation, and will pay for it; someone using AI to touch up a photo or for novelty fortune-telling does not, and would rather pay less. So run two classes on the same silicon: premium gets priority and the guaranteed low-contention resources (its tail is engineered out, per the partitioning above), so it holds its SLO at full quality; economy shares the contended pool and degrades first under pressure. Under load the economy tier absorbs the degradation that protects the premium SLO — which is exactly what lets the provider run the fleet hot instead of idling it as insurance.

Which throttle? — choosing the least-painful lever

A throttle is only as good as what it gives up. There are several ways to make a token cheaper under deadline pressure; they differ sharply in how much headroom they reclaim, how much the customer feels it, and whether they cost silicon. The honest ranking is regime-dependent — but in the memory-bound serving regime (long context, batch amortizes weights, KV dominates) one lever wins on all four axes at once.

Why KV throttle wins here — and the part that isn’t obvious. In memory-bound serving it’s the biggest term, adds no area, and is a continuous per-token knob — and with content-aware selection (Quest, on the study page) it drops the unimportant old tokens, so the measured cost is +0.12% perplexity at 75% kept. The non-obvious part is where the pain lands: KV throttling costs long-range recall specifically. That makes it nearly free for recency-dominated work (chat, a photo touch-up prompt, novelty apps) and genuinely painful for long-context retrieval (a radiologist synthesizing a long report; legal-doc QA). So the lever’s pain profile is anti-correlated with willingness-to-pay: it hurts least exactly on the economy-tier workloads you’d throttle, and most on the premium long-context work you’d never throttle (that runs full-KV on guaranteed resources). The throttle aligns itself with the tiering — which is the real reason it’s the least-painful lever for this business, not just in the abstract.
Control dynamics — a fast fine actuator over a slow coarse one. The reason to reach for KV-throttle in an imminent miss isn’t only steady-state cost — it’s bandwidth. KV-throttle (and, when compute-bound, early-exit) is decided per token, inside the decode loop — early-exit can even terminate mid-forward-pass — so it shrinks the very unit that’s about to miss: a high-bandwidth inner loop that rejects a contention spike now. Effort / token-budget throttle is a per-request control that sets how much total work a response spends — a slow outer loop, too late to save the next token. So run them as a cascade: the fast inner loop absorbs transient spikes token-by-token, and the slow outer loop sets the operating point per request and per QoS tier. Match the inner actuator to the regime’s bottleneck — cut the KV read when memory-bound, cut layers when compute-bound (this page’s Layer 1 is that fast loop; Layer 2 and effort are the slow one). Two honest asymmetries on the compute side: early-exit is not free the way a KV read-mask is (it needs trained exit heads — some area), and layers aren’t content-selectable the way KV pages are, so a deadline-forced early-exit degrades capability uniformly and can bite hardest on the hard tokens that needed the depth (CALM avoids this by exiting only when confident — a quality-preserving speedup, not a deadline throttle). For MoE models the better-targeted compute lever is trimming expert count — content-aware like KV, since the router already scores experts by relevance.
So the answer is a ladder, not a single knob. Spend the cheapest-pain lever first, matched to the regime’s bottleneck. Memory-bound (long-context decode): KV throttle is rung one. Compute-bound (prefill, large batch): schedule first (chunked prefill — no quality loss), then trim MoE experts if it’s an MoE, then early-exit for dense models; precision and cascade are coarser fallbacks; output truncation is the last resort. And “least painful” has a trust dimension — silent degradation erodes it, which is why the self-correcting speculative throttle (§5) and a disclosed SLA tier matter as much as the raw quality delta. Prior art per lever: KV — StreamingLLM, H2O, Quest; depth — CALM; precision — any-precision / dual-precision LLM serving; cascade — FrugalGPT.

05Honesty notes & the tighter analog

Which throttles are bounded, and which strain. A retransmission-style fallback (drop it, resend it — an ARQ/HARQ NACK is the networking version) is cleanly bounded: the work comes back and succeeds. Layer 2’s shed request is exactly that. Layer 1 is the strained one: a degraded token can propagate autoregressively, so its Δppl is a per-token quality proxy, not a hard recovery bound. That’s why the controller should prefer to degrade on low-stakes tokens and stay conservative. The throttle that restores the bound is speculative decoding under a deadline: accept the draft token without full verification when time is short, and a later verify pass corrects it — a true detect–fallback–recover loop. The KV-budget version’s quality axis is measured on a real model; the speculative variant, which restores the bound, is demonstrated live just below.

Model bounds. Both sims are first-order and illustrative — the shapes (cliff vs plateau) are the claim, not the absolute milliseconds. Layer 1’s compute/KV constants are calibrated so the deterministic baseline consumes its deadline slack near a realistic context, at which point the contention tail (the jitter term) drives the misses — not the deterministic read itself; its quality axis (budget→Δppl) is the real Quest measurement. Layer 2 is a single-server M/G/1-style queue with a mean-preserving 2-state burst process and a retry feedback loop; production serving adds continuous batching, multiple replicas, and priority classes, all of which move the numbers but not the phenomenon. Speculative decoding — the bounded, self-correcting throttle

Same real-time decoder, but now a cheap draft model proposes each token and the expensive target verifies it (the verify carries the contention tail). Three ways to handle a verify that won’t fit the deadline: verify-always (wait — and miss), KV-trim (shrink the target so it fits, but a trimmed verify silently passes some wrong tokens — Layer 1’s lever), and the speculative throttle (emit the draft unverified on time, then a later slack slot runs one parallel verify pass that catches and corrects the whole pending block). Watch what a contention burst does to the uncorrected-error count — not the latency, which both survivors hold.

This is the property that makes the throttle self-correcting. KV-trim and the speculative throttle both hold the deadline at ~100%, so on a latency chart they look identical — the difference is only visible on the error axis. KV-trim spends quality it can never account for; speculative decoding spends only a deferred verification that it always settles, so the loss is detectable and correctable, bounded by the backlog window rather than smeared across the whole stream. The price of that guarantee is real: a second (draft) model to run, and during a sustained burst a larger slice of the output is transiently unverified. Honest bound — in a streaming setting you cannot literally un-emit a token, so “correct” means the trajectory is fixed forward the moment the deferred verify rejects; the error is contained to the backlog window, not silently propagated. 06Where this sits in the literature

The idea is not new to computing — it is just scattered across three communities that rarely cite each other, and none of them frames the trigger the way a real-time-systems engineer does (a contention-induced deadline miss on shared compute) and ties the graceful lever to a near-memory KV datapath. That intersection is the open space.

1 · Real-time systems — the exact formalism

The classical imprecise computation model (Liu et al., late 1980s–90s) splits a task into a mandatory part and optional parts, and sheds the optional parts under deadline pressure — a bounded-accuracy loss instead of a miss. This is precisely the NACK principle. It was carried directly into deep learning by “Scheduling Real-time Deep Learning Services as Imprecise Computations” (arXiv 2011.01112, 2020), which casts a DNN as mandatory + optional stages and reports near-zero deadline violations at a small accuracy cost — the same trade this page simulates. The RT community also has anytime algorithms and deadline-aware DNN scheduling at the edge (EdgeServing; real-time work-conserving GPU scheduling for concurrent inference).

2 · Adaptive-computation ML — the graceful lever

The mechanism for a bounded-loss model output already exists: early-exit networks (BranchyNet, 2016; Shallow-Deep, DeeBERT), anytime multi-scale nets (MSDNet), and for LLMs specifically Confident Adaptive Language Modeling (CALM) (Schuster et al., NeurIPS 2022), which exits early per token with a provable quality bound vs the full model. Speculative decoding (Leviathan et al., ICML 2023) is the verify-and-correct variant — the tightest HARQ analog. But this whole line is motivated by average speedup, almost never by hard-deadline robustness under contention.

3 · ML serving systems — mostly engineer the variability away

The serving community attacks the same tail, but its instinct is to remove variability rather than degrade gracefully. “The Tail at Scale” (Dean & Barroso, CACM 2013) is the canonical statement that tail latency comes from shared-resource contention, background work, and queueing — your control-plane point, for datacenters. Clockwork (OSDI 2020) makes DNN serving predictable by eliminating variability from the bottom up. The current LLM wave — Orca, vLLM/PagedAttention, Sarathi-Serve, DistServe, Llumnix — is SLO-aware scheduling; admission control / load-shedding (this page’s Layer 2) is standard overload practice now reaching LLM serving, and recent work explicitly measures the noisy-neighbor / predictability problem on shared GPU clusters.

The whitespace. Community 1 has the deadline-miss-under-contention framing but treats the model as a black-box accuracy knob. Community 2 has the fine-grained quality lever (early-exit, KV budget) but tunes it for throughput, not deadlines. Community 3 mostly tries to make the tail disappear rather than plan a bounded-loss fallback for when it doesn’t. Almost nobody (I found no direct prior art) does all three at once: partition by criticality so the tight path runs on guaranteed low-contention resources, then absorb the residual contention tail with a near-memory KV read-budget cut whose quality cost is measured, and sell the reclaimed capacity as tiered QoS. That is the hard-real-time chip designer’s reflex — guaranteed resources first, bounded-loss backstop second, throughput as the payoff — applied to inference silicon, and it is the through-line from this page to the memory-boundary study.
