The array can't keep up

Interface speed is racing; the DRAM core has been flat for twenty years. Memory bandwidth is bought — with width, packaging, and power — not clocked. Which leaves exactly two durable moves.

A recurring question when people see the data-movement argument: interconnect keeps getting faster — GDDR7, HBM4, 224-gigabit SerDes, co-packaged optics — so surely memory bandwidth just keeps up? It does, in aggregate. But it keeps up the way a quarry keeps up with demand: not by mining faster, but by moving more rock. The thing actually storing your bits has barely sped up in twenty years, and everything else is compensation bolted around it.

Three "bandwidths" people conflate

Almost every confusion here comes from collapsing three different numbers into one word. Per-pin signaling rate — the PHY — is racing: GDDR6 at ~16–20 Gb/s, GDDR6X 22, GDDR7 32 and climbing toward 48. Note how it climbs past ~20 Gb/s: not with a faster clock but with richer modulation — PAM3/PAM4 pack more bits per symbol because you can't keep doubling the baud rate across a package. Aggregate interface bandwidth — per-pin × width — is where HBM wins, and it wins by width: HBM3e is only ~9 Gb/s/pin, but 1024 bits wide per stack gives ~1.2 TB/s; HBM4 goes to 2048 bits for ~2 TB/s. Slow per pin, absurdly wide, and glued to the die by an interposer. And then there is the number that actually answers the question — the DRAM array core rate — which has gone essentially nowhere.

For reference, Tenstorrent's Blackhole sits at 512 GB/s of GDDR6 per chip — a ~256-bit-class bus at ~16–18 Gb/s/pin on a standard organic substrate, no interposer. Cheap memory, standard packaging, Ethernet for scale-out. Hold that in mind; it's the frugal end of the same physics.

The core is flat — and it's physics, not laziness

A DRAM bit is a tiny leaky capacitor. Reading it means driving a bitline, firing a sense amplifier, and resolving a small analog charge into a digital one. That's a slow, physics-bound operation, and it has a floor. Row-cycle time (tRC) has crept from ~60 ns two decades ago to ~45–50 ns today; the array core runs a few hundred megahertz. Worse, it fights density: shrinking the cell stores less charge, which makes sensing harder and slower, not faster. There is no Moore's law for the DRAM array. So none — literally none — of the interface gains come from faster cells.

So how does interface bandwidth climb anyway? Three tricks around a slow core

Every generation buys aggregate bandwidth with the same three levers, none of which touch cell speed. Prefetch: one slow, wide read from the array — open a row, grab a large burst (a 16n prefetch on GDDR6/DDR5) — which the fast PHY then serializes out the pins. The array lumbers once; the pins stream. Banking parallelism: dozens of banks and bank-groups, interleaved so that while one bank sits in its slow tRC recovery, others are being read — you hide the slow core behind many banks running out of phase. Width and modulation: more pins (HBM's 1024/2048-bit stacks) and more bits per symbol (PAM3/4). That's the whole playbook. It works beautifully for streaming, wide, bank-parallel access — and not at all for random, narrow, latency-bound access, which stays pinned to the core rate.

So — can the array keep up? No, and structurally it can't

Aggregate memory bandwidth keeps climbing only because you keep spending pins, banks, stacks, interposers, PHY area, and I/O energy to widen and parallelize around a core that isn't getting faster. Which means bandwidth has become a cost-and-packaging problem, not a speed problem — and that is precisely why HBM is expensive. You are paying for width and 2.5D packaging to compensate for a flat array. It is also why a frugal design like Blackhole trades raw bandwidth for cost: same physics, cheaper side of the curve.

Where 224G SerDes and CPO fit — a different axis

224-gigabit-per-lane PAM4 is shipping and 448G is the 2026 frontier for 3.2 Tb/s optical modules; co-packaged optics pulls the light into the package to beat the electrical reach-and-energy wall. All of it is scale-out — chip-to-chip, node-to-node, and increasingly memory pooling — and none of it makes a DRAM array faster. Note the shape mismatch: you never run a memory PHY at 224G/pin. Memory is wide-and-moderate (hundreds of pins at 16–48 Gb/s, capacity sitting right next to compute); the fabric is narrow-and-blazing (a few lanes at 224G+ for reach). Optics attacks reach; the array core is untouched. Faster links just relocate the bottleneck inward — back to the pins-versus-array gap.

The bandwidth nobody exposes — and the two moves it leaves

Here is the fact hiding inside all of this. The array's internal bandwidth is enormous. Activating one row opens ~1–2 KB of bits into the sense amplifiers at once, per bank, across dozens of banks — the on-die bandwidth behind the pins is orders of magnitude larger than anything the interface ever exposes. HBM's entire trick is drilling more through-silicon vias to leak a little more of that internal bandwidth out through more pins. The pins are the choke; the array is not.

If the interface race can't win — because the choke is the pins-versus-array gap, not the link — then only two moves are durable: move fewer bytes across the pins, and compute before the pins.

The first is content-aware read reduction — skip the KV and weight bytes a given token doesn't need, so the scarce, expensive pin bandwidth carries only what matters. The second is near-memory compute: do the reduction at the base die, near the banks, so you exploit the array's huge internal bandwidth before the narrow, power-hungry pin interface — and return only the survivors. That is not a bonus feature of processing-in-memory; it is the reason it exists. GDDR7, HBM4, 448G, and CPO are all buying width to paper over a flat array, and paying through the nose to do it. Moving fewer bytes, and moving them a shorter distance, is the lever that doesn't depend on a physics curve that stopped bending.
