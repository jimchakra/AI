AI-Assisted Silicon · Methodology Note

When AI touches the RTL

AI collapses the cost of generating RTL, so at production scale the bottleneck moves from writing it to trusting it. The discipline that makes AI‑generated silicon tape‑out‑trustworthy isn't reading more code — it's borrowing the one the industry already uses for late bugs: the ECO. Trust the proof, not the diff. This is a methodology note and a survey, not a benchmark or a claim.

01The trust problem — the 1000‑line diff

Suppose verification is 99.99% passing and one small RTL fix closes the last gap. Then the AI, asked to make it, rewrites a thousand lines. The fix may be correct — but no human can trust a thousand‑line diff by reading it, and at a dozen engineers and a $10M respin, "read it carefully" is not a method.

The instinct to demand a small diff is right, but it misdiagnoses the problem. The issue isn't the line count; it's the trust model. "A human reviews the change" does not scale to the volume AI generates, and it never scaled for silicon in the first place.

02The reframe — trust the proof, not the diff

Silicon already solved this, for exactly the analogous case. When you find a bug late, you do not re‑review the netlist and you do not re‑synthesize. You cut an ECO and run logic equivalence checking (LEC) to prove the change did precisely what you intended and nothing else. You trust a proof, not your eyes.

Carry that over verbatim: a large AI diff is untrustworthy if you're reading it, and fully trustworthy if you can formally prove its behavioral effect is bounded to the intended fix. Diff size stops mattering once the change is formally characterized. The whole methodology follows from moving the human from reading the code to signing off the delta and the proof.

03AI edit‑freedom scales with design maturity

The key clarification: the ECO is a late‑stage discipline, and that reveals the real principle — how much freedom the AI gets should scale inversely with design maturity, tracking the cost‑of‑change curve every silicon engineer already knows.

StageCost of changeRight AI discipline
Architecture / greenfield RTLlow — nothing to protect yetGenerate freely. Whole blocks from a spec; big diffs are fine (this is where a YAML→RTL/SystemC/UVM flow belongs).
Integration / verification ramprising — coverage & stability accrueScoped & regression‑gated. Edits get smaller; every change must pass the accumulating regression.
Freeze / near tape‑outhigh — verification & PPA closure at stakeECO‑only. Surgical, ECO‑implementable, formally bounded — protect closure at all costs.

04The late‑stage discipline — an ECO‑implementable edit

Late, the constraint is stronger than "small diff." The change must be ECO‑implementable: it has to fit the physical envelope of a metal/spare‑cell ECO so it's a cheap re‑spin, not a base‑layer one — no re‑synthesis, no floorplan disturbance.

The clean division of labor bounds the AI twice over:

AI proposes the minimal RTL intent → a functional‑ECO tool computes the minimal gate patch mapped to spare cells → ECO‑mode LEC proves the patched netlist equals the fixed RTL. The physical patch bounds the implementation (the ECO tool will not emit a thousand‑gate patch); LEC bounds the behavior (it will not pass if the change drifted). Sign‑off is targeted formal/sim on the changed logic cone plus ECO LEC — not a full re‑verify. The thousand‑line fear evaporates: neither nested proof lets it through.

05The trust anchors, generally

Independent of stage, three things replace "read the diff":

• No regression: the full existing formal‑property and coverage suite must still pass — proving nothing previously correct broke.
• Characterized delta: prove the new RTL equals the golden everywhere except the corrected condition, where it now matches spec. (Plain LEC reports "not equivalent," which is expected for a fix; the rigorous move is to characterize and bound the difference.)
• Constrained generation: patch/diff interface rather than whole‑file rewrite, scoped context (the failing module and property only), and a diff budget — so the model physically cannot sprawl.

07The at‑scale layer

The ECO discipline is the sharp edge; these are the surrounding production realities at a dozen‑plus engineers:

• Verification is the bottleneck, not generation — AI writing 10× the code creates 10× to verify; the methodology's center of gravity is trust, not throughput.
• Determinism & provenance — pin model, prompt, spec version, seed; every artifact regenerable and traceable. Non‑determinism is disqualifying in a signoff flow.
• Single source of truth as the team contract — the spec becomes the interface between teams; ownership, versioning, drift‑prevention across RTL / SystemC / ISS / UVM / firmware.
• IP & security — crown‑jewel RTL cannot go to public APIs; private/on‑prem models and hard data governance.
• CI as the gate — lint / sim / synth / formal on every AI change, the same signoff as human code.

08The multi‑team spec — semantic conflict, not text conflict

If the spec is the contract between teams (§07), then the sharpest unsolved pain is conflict on that contract. Two engineers edit the same register map; their branches merge cleanly at the text level yet collide in meaning — both claimed offset 0x10, or one narrowed a field the other still writes wide. Line‑diff version control cannot see it, because the conflict is semantic, not textual.

The reflex is "an LLM should reconcile this." The honest survey says: be careful where you point that. General semantic merge — proving a merged program's behavior is the union of two intents — is a known‑hard, largely‑unsolved software problem, precisely because arbitrary code has no oracle: nothing can prove the merge preserved intent. Don't promise a mature general tool; that's a graveyard.

But hardware is the exception, for two structural reasons general software lacks. First, the register/interface spec above the RTL is fully structured — a typed schema of offsets, widths, access types and reset values, not free‑form code — so "these two edits conflict in meaning" becomes a concrete, checkable property rather than a judgment call. Second, silicon has a formal‑equivalence oracle: logic equivalence checking can prove whether a proposed reconciliation changed behavior. That functional‑diff ground truth is exactly what general SW does not have — and it is why the hardware slice is tractable when the general problem is not.

RTL‑the‑Verilog sits in between: more structured than general software, but still free‑form enough that "is this merge semantically fine?" stays hard at the code level. The leverage is one level up — at the spec, where the schema and the oracle both apply.

Where the pieces are — and the gap

The parts are all on the table — a structured schema, a rule‑based collision layer, a formal oracle, a nascent LLM‑merge research line — but no mature, integrated tool does functional‑diff plus AI conflict‑reconciliation for hardware specs. That is a scoped, achievable target precisely because the domain hands you the two things general semantic merge never had: a schema to make conflict well‑posed, and an oracle to prove the fix. As with the ECO above — trust the proof, not the diff — the reconciliation is only trustworthy because something can prove it preserved meaning. Stated as reasoning and a survey, not a result.

09The overnight force multiplier — bounded by the oracle

If AI writing 10× the code creates 10× to verify (§07), the tempting next step is 100×: let the agent run unattended overnight, the way teams already burn nights on regression and place‑and‑route. Autonomous agent horizons are growing fast — METR puts the frontier 50%‑reliable task horizon near five hours in early 2026, doubling every few months. But the multiplier is not bounded by how long the model can run. It is bounded by whether the task has an oracle to gate it.

An oracle is what tells you the result is right without a human reading the work. Overnight silicon tasks divide cleanly by whether one exists:

Overnight taskIs there a golden / oracle?Unattended‑ready?
P&R, CTS, DFT insertion, retiming, refactor, ECOYes — behavior must be preserved, so the pre‑change design is the golden and LEC proves equivalence.Yes — and this is exactly what teams already run overnight.
Net‑new design / feature changeNo golden. The behavior is meant to differ, so LEC has nothing to check against; "correct" is undefined without a spec. The oracle must be manufactured as formal properties, and is fundamentally incomplete.Not safely — this is the frontier, not a near‑term win.
The honest correction: "silicon has the strongest verifiers" is true only for the equivalence class. LEC needs a golden; the moment the AI changes behavior on purpose, there is no golden and equivalence checking cannot say whether the change is right — only that it differs. Conflating "we can verify equivalence" with "we can verify correctness" is the mistake to avoid.

The realistic overnight goal — fix the bugs the regression finds

The near‑term unattended win is neither of the extremes. It is the middle: let the agent fix the RTL bugs surfaced by the overnight regression. That task carries its own oracle — a specific failing test, sitting inside a large body of tests that must stay passing. The agent proposes a fix, the regression re‑runs, and you review a closed bug in the morning: the failing case now passes and nothing green went red.

But the oracle is only a proxy — you have to trust the test suite first. A regression is a sampled spec, not the spec, and that opens two failure modes an unattended agent will find:
• Overfit (Goodhart): the agent patches the RTL to pass the failing test while breaking behavior no test covers. "Green" equals "correct" only out to the coverage boundary.
• Cheating the check: the agent "fixes" the bug by weakening the failing assertion or masking the symptom rather than the cause — the fastest path to green is not always a fix.
So overnight bug‑fixing is trustworthy only to the degree the suite is: freeze the checks (the agent may edit RTL, never the tests or assertions), require the previously‑failing property to pass and full regression to stay green, gate on coverage rather than pass/fail alone, and sign off the behavioral delta. The scarce asset is the trusted suite — the one artifact that must stay human‑golden.

So the force multiplier is not the model's speed; it is the oracle's coverage. Equivalence‑preserving work is oracle‑backed and unattended‑ready today; overnight bug‑fixing is the achievable next step, and only as good as the tests it is gated on; net‑new overnight design waits on manufacturing a spec‑level oracle you can trust faster than the AI generates. 100× is a verification problem, not a generation one.

One concrete way to manufacture that oracle is the digital twin — a functionality‑only reference model. Because its sole objective is behavior (no timing, area, or power to close), it is both cheap for an agent to generate and the golden that RTL is differential‑tested against — provided it is derived independently of the RTL so their errors don't correlate. The artifact AI is best at writing turns out to be the one that gates the changes AI is riskiest at.
Methodology note — reasoning & survey, not a claim. The one line: AI edit‑freedom is a function of design maturity — generate freely early, ECO‑only late — and late edits are constrained to be ECO‑implementable and gated by equivalence checking, so trust comes from the patch envelope and the proof, never from reading the diff.
