Architecture Methodology

How a principal engineer runs SoC design

Two disciplines make silicon arrive working: deciding the architecture on simulation evidence with the biases named, and executing it so firmware and DV are done at tape-out — not discovered 6–18 months later. This is the approach behind the essays and the working demonstrator.

Part 1  Deciding the architecture — a bias-aware sequence

Each phase has a known optimism/pessimism bias. Knowing those biases — and correcting them with the right model — is what separates a principal architect from someone reading a datasheet.

01
Product envelope
Target band, UE/CC count, throughput, power, form factor — grounded in a reference platform and the target delta.
sets the design point — wrong here, wrong everywhere downstream
02
Static latency analysis
Single-path critical chain with dedicated resources, no contention.
⚠ over-optimistic — dedicated resources don't exist when N channels run at once
03
Static peak analysis
Worst-case simultaneous load; sizes coprocessor counts from first principles (the classic "static Excel").
⚠ over-pessimistic — worst case on every dimension rarely coincides
04
Contention simulation
Discrete-event model (SimPy): concurrent load, priority queuing, stochastic durations. Finds true P99 under real contention.
corrects both biases — some paths worse than static, some better
05
DVFS analysis
Config → Fmin at 5–10% margin → voltage from the DVFS curve → power estimate. Validates frequency scaling before committing silicon.
de-risks power before RTL
06
Architecture decisions
Findings drive engine counts, SRAM topology, real-time/soft partition, process-node choice; area validates feasibility.
grounded in simulation evidence, not intuition
Why static analysis alone is insufficient. Static latency assumes dedicated resources; under concurrent load P99 can run 20–30% higher. Static peak assumes worst-case everywhere at once; a scheduler that "fails" the budget on paper is often a priority-blocking artifact, not a capacity problem — and the fix is priority aging or offloading the soft task off the hard-real-time resource, not more silicon. Simulation's output isn't a pass/fail verdict; it's a set of architectural questions — where is margin tight, where is priority the real constraint, where does offload buy the most headroom.

Part 2  Executing it — concurrent RTL / FW / DV from one source

The goal: silicon that arrives with working firmware and closed DV, not a chip that triggers months of post-silicon discovery.

The traditional dead zone

HLS → LLS → RTL tape-out → chip arrives → FW starts → DV starts. LLS is a late DV artifact; FW and DV wait for silicon. Bring-up becomes discovery: register mismatches, wrong interrupt timing, undocumented DMA behavior — each a respin risk.

Single source of truth

A YAML micro-arch spec — state machines, register maps, pipeline stages, interrupt/DMA behavior, timing — fans out to RTL, a cycle-accurate SystemC HW model, an ISS running real FW binaries, FW headers, and the UVM environment. Consistency is guaranteed by construction, not by cross-team review.

SystemC (~MHz) + ISS (near real-time) are the digital twin of future silicon+FW — RTL simulation is bit-true but 10⁴–10⁵× too slow to develop real firmware against. The architect owns the twin as a living spec: any RTL divergence is a bug in RTL, not the spec.

Part 3  Where AI fits

The single-source fan-out is exactly the "code-like" work an AI assistant accelerates: one YAML micro-arch spec generating RTL parameters, FW headers, DV config, and test scaffolding. The methodology is native to AI-assisted generation — but the value is the harness around it. A bit-exact golden reference, lint, exhaustive simulation, and logic-equivalence are what make generated output trustworthy; AI multiplies throughput on the generation, gated by that harness.

This is real, at two scales — with numbers. On a ~200-core 6G RU/DU SoC (TSMC N3E), the contention model inverted the static conclusion: static analysis predicted the DL scheduler failing, but simulation showed the 80.6% miss was priority inversion — 20 hard-real-time jobs per slot blocking it — not capacity. The fix was offloading the soft scheduler off the hard-real-time resource, recovering ~80 µs with no added silicon. The same study quantifies the small-frees-big economics directly: a fixed-function LDPC decode engine is ~0.1 mm² at 5 nm versus ~1.5 mm² and 5–10 W for an equivalent GPU SM (16× HW-over-SW) — and it shows why static alone misleads: true P99 runs 20–30% higher under contention (PUSCH closed at 180 µs, 42% margin on a 308 µs budget). Full study: 6g_du_rd_ai.html. The near-memory demonstrator is the front of Part 2 in miniature — one tile.yaml fanning out to RTL params, an FW header, and DV config with a CI drift-check; a bit-exact golden; verified RTL; lint/sim/synth/LEC in CI. The full SystemC/ISS/UVM concurrency is the methodology on shipping silicon, not this toy — stated plainly so the boundary is clear.
