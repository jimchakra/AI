The bandwidth budget

Decode is bandwidth-bound, so the way to more inference capacity is not more compute — it is moving fewer bytes. A first-order full-system model (compute die + memory die) of content-aware KV read-selection on a Tenstorrent Blackhole-class chip: 2–3× decode capacity at the same die and the same 300 W. 01The result — total system capacity, iso-die & iso-power

Not per-token latency — capacity: how much work the same chip does at the same wattage. At the safe operating point (content-aware KV read-selection, ~57% of KV read, ≤1% perplexity on Qwen2.5-1.5B), on 8 K context serving:

Why these are one number, not four. All four are the same ceiling — tokens/s = bandwidth ÷ bytes-per-token — read four ways. Throughput and efficiency fall straight out of it; concurrency is the freed DRAM letting more sequences fit; SLO-goodput is that capacity measured under a fixed latency percentile. The throughput gain is not the per-token speedup (~1.7×) times the batch gain (~2.3×) — both live under the same 512 GB/s, so they don't multiply. The model enforces the identity so the number can't drift upward.

03Where decode sits — the roofline

Blackhole feeds ~745 TFLOPS of FP8 from 512 GB/s: the roofline ridge is at ~1,455 FLOP/byte. Prefill (compute-bound, parallel) runs up near the ridge — that is what the MAC array is sized for. Decode is a different phase on the same silicon: batch-1 lives at 2–3 FLOP/byte, ~500× below the ridge, and no batch size climbs off the memory-bound floor (arithmetic intensity asymptotes near 34). Drag the batch to watch the serving point walk up the slope — never to the ridge.

04What the cut buys

The centerpiece. Content-aware KV read-selection removes a fraction of KV reads; because decode is memory-bound, capacity rises by ~1/(1−cut) — until the quality curve stops you (not the compute wall — the ridge is never reached). The other lever — precision — is portable, and it picks a different regime

Read-selection is one way to move fewer bytes; low precision is the other. They are worth separating, because one is architecture-specific and one is not — and because weight precision, the obvious knob, is the wrong lever for serving. Dropping weight precision (FP8 → MXFP4, ~4.25 bits) barely moves serving throughput: in the batched, long-context regime weights are amortized over a batch of hundreds and KV dominates, so MXFP4 weights buy ~1.04×. Weight precision only pays in the weight-bound corner — batch-1, short context — where it buys ~1.9× and selection does nothing. The precision lever that actually stacks with selection is on the KV cache itself (FP16 → FP8/INT4), because that hits the term that dominates serving:

Portable vs differentiating — stated plainly. Precision, weight or KV, is portable: every GPU stack already does it. So the ~4× full stack is the total byte reduction available to anyone, not an edge — and I don't claim it. The architecture-specific slice is the ~2× enforce-at-memory selection a GPU can't do at the array, because it still reads then discards. This panel is here for completeness: to size the whole byte budget, to show that the two levers dominate mutually-exclusive regimes (so they don't naively multiply), and to be explicit about which slice is actually mine.

05Does decode even matter? — the prefill/decode split

A decode win only matters if decode is where the time goes. Prefill is a fast parallel burst; decode is sequential and memory-bound, re-reading weights+KV every token. So the split is set by the prompt:generation ratio — and for anything with real generation, decode is nearly all of it. Set a workload; the bar is where the wall-clock goes, and the stat is the end-to-end speedup your current cut delivers (Amdahl).

08Honesty — the bounds this model states out loud

This is a first-order model: absolute tokens/s are directional (a cycle-accurate model refines constants, not conclusions); the shapes and crossovers are the claim. What it will not let you overclaim:

1. Single-chip capacity caps KV share ~78%. Weights (~7 GB) plus resident KV must fit 32 GB, so KV can never exceed ~78% of reads on one chip — the ~85–95% KV-share regime is a multi-chip case (KV sharded over the fabric), deferred here, not assumed.
2. The 2–3× is decode-heavy serving. Section 04 is the boundary: short-prompt-huge-output (reasoning, agentic, code) is ~100% decode and gets the full gain; encode/embedding and classify are prefill-dominated and get little. Training is compute-bound and out of scope.
3. Capacity is not free compute. The MAC array is sized for prefill/training; decode leaves it ~1–2% used because it is bandwidth-bound. The gain comes from moving fewer bytes within a fixed bandwidth budget — and argues for decode-specialized silicon that rebalances area from MACs toward memory, not for adding MACs.
4. Quality is the ceiling, measured. The cut→quality curve is a real model (Qwen2.5-1.5B / WikiText-2), not an assumption — directional for a 70B/128K deployment, not a datasheet guarantee.

09How to read this — method & where microarchitecture enters

Two questions a silicon architect will ask, answered up front.

“Is this static capacity analysis?”

Yes — the headline results are static capacity analysis: steady-state resource-balance (roofline), not cycle- or event-accurate simulation. On the ladder static peak → contention sim → RTL co-sim, this is the first rung, deliberately. The roofline core (time = bytes ÷ bandwidth, throughput = BW ÷ bytes-per-token, max-batch = DRAM ÷ footprint) has no time axis, no transients, no warmup; it assumes a full pipeline, uniformly achievable bandwidth (folded into η), and compute overlapped behind memory. Two pieces do add dynamics: the QoS panel is a stochastic M/G/1 queueing sim (it produces the tail static analysis can’t), and the race is a deterministic scheduler (arrivals, admission, changing batch) wrapped around a static per-step kernel. None of it models memory-controller queuing, bank conflicts, refresh, or NoC congestion over time — that is the next rung and needs the internals below. Static is the right tool here because the claim is a ratio at matched operating points, and decode is a near-steady-state streaming workload; the omitted dynamics hit both sides of an apples-to-apples roughly equally and cancel.

“How did you get a result without core/thread, tensor, NoC, TCM detail?”

Because the model consumes only three datasheet numbers — DRAM bandwidth, DRAM capacity, and (loosely) peak FP8 to locate the ridge — plus closed-form byte/FLOP accounting. Everything you listed lives inside the single efficiency factor η = achieved ÷ peak bandwidth: core and thread count, the matrix engine, the NoC/bus fabric, TCM/L1, kernel and scheduler overhead. Since the apples-to-apples is the same silicon running the same stack, η is identical on both sides and divides out — the speedup is bytes-baseline ÷ bytes-throttled, pure workload arithmetic. And decode runs the compute fabric at ~1–2% utilization (≈500× below the ridge), so its exact capability doesn’t gate decode throughput anyway. I calibrated η to Tenstorrent’s published 350 tok/s/user rather than deriving it — precisely because I don’t have the internals. What those internals would change:

So the 2× is robust — it survives not knowing the internals, because it is a bandwidth-bound ratio in a regime where the compute fabric is idle and η cancels. The absolute throughput and the on-chip mechanism (residency, gather, precision-format mapping) are where NoC/TCM/tensor detail would refine or challenge the picture — that is the cycle-accurate / RTL co-sim layer this model is the front-end to, not a substitute for.
